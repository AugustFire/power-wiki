# power-wiki 当前产品差距审视

> 审视时间：2026-07-27  
> 产品定位：团队内部使用的 Confluence 风格知识库  
> 设计基准：桌面端 2560×1440，最小宽度 1280px

## 一、审视范围与结论

本次审视基于当前代码，不以理想功能清单为依据。

产品约束：

- 空间用于不同团队隔离，一般不允许跨空间操作。
- 普通用户通常不会超过 5 个空间。
- 个人空间仅所有者和管理员有权限，不承担社交属性。
- 当前处于开发和打磨阶段，不以生产部署为目标。
- 本轮不评估安全、外网暴露和生产部署问题。
- 本轮不评估全文检索、comment 优化、reaction、通知、历史、最近页面活动。

### 总体判断

当前项目已经不是简单的 Wiki MVP，核心骨架已经比较完整：

- 页面树、页面层级、拖拽移动、复制、删除、恢复
- 阅读页、编辑页、自动保存、版本边界
- 标签、附件、Markdown 导入、HTML/Markdown/PDF 导出
- Tiptap 富文本编辑器、Slash 菜单、表格、代码块、折叠块、引用等
- 团队空间与个人空间
- viewer / editor / admin 三档空间角色
- 用户组、空间授权、人员管理
- 空态、骨架屏、错误反馈、面包屑、TOC
- 管理后台、设置抽屉、帮助和快捷键

当前最大的差距不是“缺少大量基础功能”，而是：

1. 高频操作入口不完整。
2. 空间生命周期还没有闭环。
3. 成员与权限的用户心智不够清晰。
4. 一些已有能力分散、隐藏或表达不一致。
5. 页面组织和内容浏览的信息密度还不够像成熟知识库。

建议下一阶段不要继续大面积横向加功能，而是优先修复核心流程中的断点。

---

## 二、优先级定义

### P0：必须优先修复

不修复会直接影响团队隔离、知识沉淀或核心任务完成；或者会造成明显的失权、误解、丢失感。优先考虑复用现有 API 和组件快速补齐。

### P1：应该尽快完善

核心任务仍然可以绕行，但会明显增加操作成本，降低空间管理清晰度，或暴露较明显的未完成感。

### P2：后续打磨

属于视觉细节、效率增强、规模化运营能力或结构性重构。当前内部、小规模使用时可以后置。

# 三、P0：优先修复的核心问题

## P0-1：阅读页缺少“复制页面”入口

### 当前现象

阅读页顶部已经有导出、历史、关注、限制、分享、编辑等操作，但“复制页面”按钮整段被注释掉了。

用户如果正在阅读一篇页面，想基于它创建一份副本，必须：

1. 找到左侧页面树。
2. 找到当前页面。
3. 打开页面树菜单。
4. 再点击复制。

### 存在的问题

复制是团队知识库里的高频动作，例如：

- 复制会议纪要。
- 复制项目文档。
- 复制流程说明。
- 复制一份页面后再修改。

当前复制 API 和 Store 能力已经存在，缺的只是阅读流中的入口。这属于“功能已经做好，但用户找不到”的问题。

### 代码依据

- `apps/web/src/views/ReadView.vue:572-583`
- `apps/api/src/routes/pages.ts`：已有 duplicate 路由
- `apps/web/src/stores/pages.ts`：已有复制逻辑

### 建议

恢复阅读页顶部的复制按钮，并在复制完成后：

- 自动跳转到新页面。
- 页面标题保留“复制自”前缀。
- 给出明确的成功状态。
- 新页面在当前页面同级位置出现。

---

## P0-2：新建页面不能方便地选择任意父页面

### 当前现象

页面树中可以：

- 新建同级页面。
- 新建子页面。
- 拖拽页面改变层级。
- 移动页面到其他位置。

但是，如果用户想“在某个较深的页面下面创建新页面”，通常必须先在左侧展开页面树，找到目标页面，再通过目标节点菜单创建。

如果目标节点被埋在多层目录中，操作成本会明显上升。

### 存在的问题

页面树适合浏览，不适合承担所有创建操作。

成熟知识库通常允许用户在创建页面时直接选择位置：

> 新建页面 → 选择所属空间 → 选择父页面

当前项目中已经存在 `PathPicker`，但主要服务于导入或移动相关场景，没有成为普通新建页面的通用入口。

### 代码依据

- `apps/web/src/components/editor/PathPicker.vue`
- `apps/web/src/components/editor/ImportMarkdownModal.vue`
- `apps/web/src/components/layout/PageTree.vue`
- `apps/web/src/router/index.ts`：已有 `/new?parent=:id` 相关路由能力

### 建议

统一页面创建入口：

- “新建页面”打开创建流程。
- 创建流程中提供“存放位置”。
- 默认使用当前页面的父级。
- 用户可以通过 `PathPicker` 选择任意父页面。
- 从页面树菜单进入时，自动预填当前位置。

这样可以同时保留页面树快捷创建和全局创建两种方式。

## P0-3：个人空间写入规则需要统一收口

### 当前现象

个人空间的权限规则已经存在：

- 所有者可以读写。
- 管理员可以查看。
- 管理员不能随意修改个人空间内容。
- 团队空间可以由不同角色协作。

但个人空间判断和写保护逻辑分散在多条路由和多个业务流程中。

### 存在的问题

这不是当前已经暴露的安全漏洞，而是产品规则容易漂移：

- 页面创建要判断一次。
- 页面编辑要判断一次。
- 页面删除要判断一次。
- 复制要判断一次。
- 附件操作还要再判断一次。
- 将个人页面发布到团队空间又有一套判断。

以后新增功能时，如果漏掉某一个判断，个人空间的产品定义就可能被破坏。

### 代码依据

- `apps/api/src/lib/personalSpaceGuard.ts`
- `apps/api/src/lib/permissions.ts`
- `apps/api/src/routes/pages.ts`
- `apps/web/src/stores/spaces.ts`
- `apps/web/src/views/EditView.vue`
- `apps/web/src/views/PublishToSpaceMenu.vue`

### 建议

先建立“个人空间写入矩阵”：

| 操作 | 所有者 | 全局管理员 | 其他用户 |
|---|---:|---:|---:|
| 查看个人空间 | 是 | 是 | 否 |
| 创建页面 | 是 | 否 | 否 |
| 编辑页面 | 是 | 否 | 否 |
| 删除页面 | 是 | 否 | 否 |
| 上传附件 | 是 | 否 | 否 |
| 发布到团队空间 | 是 | 否 | 否 |

然后所有写接口统一复用一个明确的判断入口，并为这些操作补回归测试。

重点不是增加复杂的安全系统，而是保证个人空间这个产品概念长期稳定。

## P0-4：空间失权、删除、切换后的反馈不够友好

### 当前现象

用户正在查看某个空间页面时，如果：

- 管理员撤销了他的权限。
- 空间被删除。
- 空间变成不可访问。
- 当前空间状态发生变化。

用户很可能只看到 404，或者被回退到其他空间，但不知道发生了什么。

### 存在的问题

对于用户来说，“页面不存在”和“我没有权限访问”是完全不同的事情。

当前空间模型已经强调团队隔离，因此空间切换和空间访问失败的反馈应该非常清楚。否则用户会误以为：

- 页面被误删。
- 数据丢失。
- 系统出错。
- 自己的编辑没有保存。

### 代码依据

- `apps/web/src/stores/spaces.ts`
- `apps/web/src/components/layout/SpaceSwitcher.vue`
- `apps/web/src/router/index.ts`
- `apps/web/src/views/NotFoundView.vue`
- `apps/api/src/routes/spaces.ts`

### 建议

当当前空间不可访问时：

1. 清理当前空间状态。
2. 自动回退到第一个可访问空间。
3. 给出明确提示：“你已无法访问该空间，该空间可能已被归档或删除”。
4. 如果空间仍存在但页面不存在，才显示页面级 404。
5. 编辑中发生失权时，优先提示保存状态，再跳转。

# 四、P1：影响成熟度和日常效率的问题

## P1-1：空间没有“归档”状态

### 当前现象

当前空间生命周期主要是：

- 创建
- 修改
- 删除

团队项目结束后，如果不想继续显示这个空间，只能删除。但删除前还可能要求先清理页面。

### 存在的问题

团队空间通常需要保留历史知识，例如：

- 已结束项目。
- 旧产品版本。
- 历史团队资料。
- 已停用业务线。

直接删除会让管理员在“继续占用空间”和“删除资料”之间做选择。

### 建议

增加空间归档：

- 归档后从普通空间切换器中隐藏。
- 页面保留可读。
- 默认禁止新增和编辑。
- 管理员可以恢复。
- 归档空间单独放入“已归档空间”。
- 删除仍然作为更重的最终操作。

页面级软删除和空间级归档不是同一个概念，不能互相替代。

---

## P1-2：成员管理是管理员视角，不是空间成员视角

### 当前现象

当前成员和权限能力分散在：

- People
- Groups
- SpaceEdit
- SpacePermissions

用户可以被直接授权，也可以通过用户组继承权限，但在空间层面不一定能直观看到：

- 当前空间有哪些成员。
- 每个成员最终是什么角色。
- 权限来自哪个组。
- 是直接授权还是继承授权。

### 存在的问题

管理员需要自己推导最终权限，普通用户也无法理解：

> 我为什么能访问这个空间？  
> 我到底是 viewer 还是 editor？  
> 我是被单独授权，还是因为加入了某个组？

### 建议

在空间管理页增加统一的“成员”视图：

| 成员 | 最终角色 | 权限来源 | 可执行操作 |
|---|---|---|---|
| 张三 | editor | 产品组 | 调整 / 移除 |
| 李四 | viewer | 直接授权 | 调整 / 移除 |

考虑到普通用户空间通常不超过 5 个，重点应该是“看得懂、改得快”，而不是构建复杂的企业级组织架构。

---

## P1-3：缺少邀请、加入、退出空间的最小闭环

### 当前现象

目前主要是管理员从后台给用户或用户组授予空间权限。

缺少更完整的空间成员动作：

- 邀请某人进入空间。
- 用户接受邀请。
- 用户查看待处理邀请。
- 用户主动退出空间。
- 用户被移出空间后的状态反馈。

### 存在的问题

空间对于用户更像一个“后台分配的权限容器”，而不是一个清晰的团队工作区域。

即使是内部使用，也会出现：

- 新成员不知道如何进入空间。
- 管理员不知道是否已经完成授权。
- 用户无法主动退出不再参与的空间。
- 被移除后只看到 404。

### 建议

当前阶段可以先做最小闭环：

1. 空间管理员选择用户。
2. 授予空间角色。
3. 用户在空间列表中看到该空间。
4. 空间详情页显示当前角色。
5. 用户可以主动退出非个人空间。
6. 被撤权后显示明确反馈。

个人空间不开放退出、邀请或社交成员逻辑。

---

## P1-4：页面树菜单偏长，低频操作干扰高频操作

### 当前现象

页面节点菜单中同时放置了：

- 新建同级
- 新建子页
- 重命名
- 复制
- 复制子树
- 移动
- 发布到其他空间
- 提升为根页面
- 删除
- 其他操作

### 存在的问题

页面树是用户每天使用最多的区域之一。高频动作和低频动作混在一起，会让菜单显得复杂。

### 建议

主菜单只保留高频操作：

1. 新建子页面
2. 新建同级页面
3. 重命名
4. 复制
5. 移动
6. 删除

以下操作收进“更多操作”：

- 复制整棵子树
- 提升为根页面
- 发布到其他空间
- 其他低频管理动作

不要把所有操作都藏进 kebab 菜单；页面树仍应保留一个明显的节点操作入口，只是减少首屏噪音。

### 代码依据

- `apps/web/src/components/layout/PageTree.vue`
- `apps/web/src/components/layout/Sidebar.vue`

---

## P1-5：阅读页的子页面列表信息密度不足

### 当前现象

页面底部的子页面区域主要是简单文本链接。

而首页的根页面卡片已经有摘要、子页面数量、更新时间等信息。

### 存在的问题

当一个页面下有多个子页面时，用户很难快速判断：

- 哪个页面值得先看。
- 哪个页面最近更新。
- 页面大概讲什么。
- 子页面是否已经有内容。

当前体验更像一个目录，而不是一个内容导航区。

### 建议

将子页面列表升级为轻量卡片：

- 页面标题
- 一行摘要
- 子页面数量
- 最近更新时间
- 页面图标或文档类型标识

不需要引入复杂缩略图，也不需要图片预览。

### 代码依据

- `apps/web/src/views/ReadView.vue`
- `apps/web/src/views/HomeView.vue`

## P1-6：附件管理仍然像“页面底部附属物”

### 当前现象

附件集中在页面底部折叠区域，主要提供：

- 文件名
- 文件大小
- 文件类型图标
- 下载
- 删除

### 存在的问题

当页面附件较多时，用户难以完成：

- 快速定位某个附件。
- 按类型筛选。
- 批量整理。
- 替换旧文件。
- 发现同名文件。

### 建议

仍然遵循当前项目约束：不做文件内嵌预览，不建设全局媒体库。

可以先增加页面级附件管理能力：

- 附件数量较多时显示搜索框。
- 按类型筛选。
- 显示上传时间和上传者。
- 支持重命名。
- 支持替换文件。
- 支持批量删除。
- 上传中显示明确进度和失败重试。

### 代码依据

- `apps/web/src/components/page/AttachmentsSection.vue`
- `apps/web/src/composables/usePageAttachments.ts`
- `packages/shared/src/constants.ts`

## P1-7：全局 Home 和个人工作台入口不够明确

### 当前现象

顶栏没有一个稳定、明确的 Home 入口。

用户通常需要：

- 点击侧边栏当前空间名称。
- 通过用户菜单进入个人工作台。
- 依赖当前页面的面包屑返回。

### 存在的问题

在深层页面、管理页或设置页面中，用户缺少一个稳定的“回到主界面”锚点。

个人空间和团队空间也没有完全统一的入口心智：

- 团队空间首页偏空间导航。
- 个人工作台偏个人内容汇总。
- 入口分散在不同位置。

### 建议

至少提供以下一个稳定入口：

- 品牌 Logo 点击回到当前空间首页。
- 顶栏增加明确的 Home 按钮。
- 用户菜单继续保留“我的工作台”。
- 当前空间名称点击回空间首页。

### 代码依据

- `apps/web/src/components/layout/TopBar.vue`
- `apps/web/src/components/layout/Sidebar.vue`
- `apps/web/src/components/layout/UserMenu.vue`
- `apps/web/src/views/HomeView.vue`
- `apps/web/src/views/MeDashboardView.vue`

## P1-8：管理入口语义分裂

### 当前现象

管理能力分散在多个入口：

- 顶栏的空间管理按钮。
- 用户菜单中的管理后台。
- 空间切换器空态中的管理入口。
- 空间详情中的权限设置。

### 存在的问题

用户很难判断：

- 哪个入口是管理当前空间。
- 哪个入口是管理所有空间。
- 哪个入口是管理用户和用户组。
- 哪个入口需要全局管理员权限。

### 建议

将管理概念分成两层。

### 当前空间管理

放置：

- 空间名称与描述
- 空间成员
- 空间角色
- 页面级默认行为

### 全局管理

放置：

- 所有空间
- 所有用户
- 用户组
- 审计
- 系统级配置

顶栏只保留一个统一的“管理”入口，根据权限进入对应层级。

### 代码依据

- `apps/web/src/components/layout/TopBar.vue`
- `apps/web/src/components/layout/UserMenu.vue`
- `apps/web/src/components/layout/SpaceSwitcher.vue`
- `apps/web/src/views/manager/ManagerLayout.vue`
- `apps/web/src/views/manager/SpaceEditView.vue`

# 五、P2：后续打磨项

## P2-1：页面树缺少批量操作

### 当前现象

页面只能逐个移动、打标签、删除或导出。

### 存在的问题

页面数量增加后，整理页面会变得非常耗时。

### 建议

后续增加：

- 多选页面
- 批量移动
- 批量删除
- 批量添加标签
- 批量导出

当前用户空间数量较少、项目仍在打磨期，因此优先级低于空间成员和核心入口。

---

## P2-2：空间级导出能力不足

### 当前现象

当前主要是单页面导出。

### 存在的问题

当一个团队结束项目或需要迁移资料时，管理员无法方便地整体导出一个空间。

### 建议

后续支持空间级导出：

- 页面内容
- 页面层级
- 标签
- 附件文件
- Markdown 或 HTML 格式
- ZIP 打包

---

## P2-3：PDF 导出名称和实际行为不完全一致

### 当前现象

界面提供“PDF”选项，但实际通过浏览器打印对话框保存 PDF。

### 存在的问题

用户预期的是“一键生成文件”，实际却需要手动选择打印目标和参数。

### 建议

短期先把文案改为“打印 / 另存为 PDF”。后续如果确实需要，再实现真正的 PDF 文件生成。

### 代码依据

- `apps/web/src/components/editor/ExportMenu.vue`

## P2-4：Markdown 导入更适合单篇内容，不适合团队迁移

## P2-5：2560×1440 屏幕下部分区域存在空间利用率问题

### 当前现象

项目设计目标是 2560×1440，但部分管理页内容仍使用较窄的固定最大宽度。

### 存在的问题

在大屏上可能出现：

- 两侧留白较大。
- 表格没有充分利用空间。
- 管理信息需要更多滚动。
- 管理页与主编辑页面的信息密度不一致。

### 建议

围绕 2560×1440 做一次完整的版心检查：

- 页面阅读区宽度
- 管理三栏宽度
- 表格列宽
- 空间卡片密度
- 右侧 TOC 宽度
- 页面树可见宽度

不要通过移动端断点解决，项目明确是桌面端产品。

### 代码依据

- `apps/web/src/views/manager/PeopleView.vue`
- `apps/web/src/views/manager/AuditView.vue`
- `apps/web/src/views/manager/ManagerLayout.vue`

## P2-6：顶部页面结构和 Sidebar 挂载位置分散

### 当前现象

部分顶层页面自行挂载 Sidebar，部分页面使用不同的页面壳，公共布局契约分散在多个 View 中。

### 存在的问题

以后新增页面时容易出现：

- 忘记挂 Sidebar。
- 顶栏高度不一致。
- 面包屑位置不一致。
- 空态页面和正常页面左右边距不同。

### 建议

后续可以将公共壳层统一为：

```text
AppShell
├── TopBar
├── Sidebar
└── RouterView
```

但这属于结构性重构，应在核心功能稳定后做，不建议现在为了架构统一而大面积改动。

# 六、建议的落地顺序

## 第一阶段：修复核心断点

1. 恢复阅读页“复制页面”。
2. 普通新建页面支持选择父页面。
3. 统一个人空间写保护入口。
4. 优化空间失权、删除、切换后的提示。
5. 统一当前空间首页入口。

这一阶段不需要新增大型数据模型，主要是复用现有 API 和组件。

## 第二阶段：完善空间管理闭环

1. 空间归档与恢复。
2. 统一空间成员视图。
3. 显示权限来源和最终角色。
4. 增加最小的邀请、加入、退出流程。
5. 区分当前空间管理和全局管理。

这是从“管理员能配置”走向“团队能理解和使用”的关键阶段。

## 第三阶段：提升内容组织效率

1. 子页面卡片化。
2. 页面树菜单分层。
3. 页面级附件管理。
4. Markdown 批量导入。
5. 页面树批量操作。
6. 空间级导出。

## 第四阶段：整体产品抛光

1. 2560×1440 版心和信息密度优化。
2. 顶层页面面包屑统一。
3. 清理 disabled 占位入口。
4. 统一 Sidebar / AppShell。
5. 修正文案和“功能名称与实际行为不一致”的地方。

# 七、本轮不建议投入的事项

# 八、最终判断

当前项目的基础功能覆盖率已经不错，下一阶段的核心不应是继续增加功能数量，而应围绕三个问题打磨：

1. **用户能不能快速找到正确的入口？**
2. **管理员能不能看懂空间和成员关系？**
3. **空间从创建、使用到结束，是否有完整且可理解的生命周期？**

如果只选择最值得立即做的三项，建议优先：

1. 恢复阅读页复制入口。
2. 完善空间成员和归档生命周期。
3. 统一空间首页、个人工作台和管理入口的全局导航心智。
